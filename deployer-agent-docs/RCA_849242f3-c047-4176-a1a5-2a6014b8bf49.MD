# RCA — estimate-home "graves problèmes de performances" (resource saturation)

Run: 849242f3-c047-4176-a1a5-2a6014b8bf49 (live) · Tier: tier_0 "Starter" · 2 replicas · HPA/VPA off

## Verdict
**Saturated resource = MEMORY, not CPU.** The single app container is being **OOMKilled** against the 512Mi limit. CPU is not the bottleneck.

## Evidence
- Pod events: `last_termination: OOMKilled, exit_code 137, restarts=2`, kill_findings confirm the container was OOMKilled (most recent at 2026-11-10T11:57:02Z).
- tier_0 limits: memory **request 128Mi / limit 512Mi**, cpu 50m/250m. No autoscaling.
- Correlated unresponsiveness before a restart: nginx logs show `upstream timed out (110) while reading response header ... GET /health` at 13:41–13:42, then `connect() failed (111: Connection refused) ... /health` at 13:43:34→13:44:14 (backend down / restarting), then `Application startup complete` at 13:44. Classic pre-OOM GC-thrash → kill → restart window. Live /health is slow-ish (529ms).

## Memory baseline drivers (startup, sustained — not request spikes)
Single container runs nginx + uvicorn (`--workers 1`) + serves the Expo web export (`Version Web servie depuis /app/backend/webdist`) + loads ML artifacts and the DVF dataset at startup:
- `model_store - Model hedonic_v2 seeded from disk` and `Model ml_lgbm_v1 seeded from disk (newer artifact)` — two models resident in RAM.
- **CODE BUG inflating the baseline:** `server - WARNING - DVF_DEPARTMENTS (env, 3 départements) ignoré : couverture France entière (97) appliquée`. The `DVF_DEPARTMENTS` env var requesting only 3 départements is **ignored**, and the **whole-France DVF dataset (97 = all departments) is loaded instead** — a large, avoidable memory baseline. This is the single biggest lever.

## Request-side load (secondary; not the root cause)
- Heavy per-request endpoints seen: LiteLLM `gemini/gemini-3-flash-preview` calls (photo retouch / analysis), bursts of `/api/properties/*/market-signal|trend|risks`, geocode autocomplete bursts (`/api/geocode?q=...` fired per keystroke). On a single uvicorn worker these add transient memory + latency on top of an already-high baseline.
- Proxy/crawler: traffic arrives via one GCLB egress IP (34.49.222.149 — the achetemamaison.fr proxy). Mostly legitimate; some vulnerability-scanner probing (`/.env`, `/.aws/credentials`, `/vercel.json`, etc. → 19× 404). Noise, not the memory cause.

## NOT the cause
Recent deploys (backend/media/*.mp4 ~12MB static files, `X-Robots-Tag` header) do not drive RAM — mp4s stream from disk; the header is trivial. Infra unchanged.

## Fix
**Two independent actions, do both:**
1. **Source fix (real fix, biggest win):** make DVF loading honor `DVF_DEPARTMENTS` so only the 3 requested départements load instead of all of France. Investigate why the env value is parsed then discarded with the "couverture France entière (97) appliquée" fallback. This should cut the startup memory baseline substantially and may let the app stay on a low tier.
   - Secondary source improvements: consider lazy-loading / memory-mapping the ML models and DVF data instead of holding everything resident; cap/debounce `/api/geocode` autocomplete server-side.
2. **Immediate relief (User, from Deployment Panel → Resources):** upgrade from tier_0 (512Mi) to **tier_1 "Launch"** to stop the OOMKills now. If the DVF fix lands and baseline drops, the tier can be reassessed.

Note: OOM + the DVF data load could not be reproduced in the eph sandbox (it has more memory, no secrets, and not the DVF data files) — this RCA is diagnosed from production pod events + logs, not eph-reproduced.
